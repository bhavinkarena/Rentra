THE SEQUENCING PRINCIPLE

Supply first, and two gates, not one.

The roles do not come online at the same time, and the order is not a preference — it is forced. A Customer who lands on an empty search page never returns, so Client onboarding must work before Customer signup exists at all. And Super Admin has to exist before either, because both gates are staffed by a person.

Why two gates and not one

You identified this correctly and it is the single most important structural decision in the flow. Approving a person is not the same as approving a property.

The two gates do different jobs

One gate is the failure mode to avoid. If you only approve accounts, an approved Client can publish a farmhouse they found on Instagram. If you only approve listings, you have no verified party to pay, no KYC on file, and no recourse when a payout is disputed. Both gates, always, and Gate 2 re-fires on edits — see trust fields.

Login is per role, because an account is one role

An account carries exactly one role, fixed at signup, so the role cannot be inferred from a credential. Each role therefore gets its own entry point and its own credential type.

Authentication by role
RoleRouteCredentialAlso verifiedSelf-signup?

Customer /login Phone + 6-digit OTP Email optional; KYC above ₹5,000 booking value Yes — instantly active
Super Admin /admin/login Email + password + TOTP — Never. Seeded or invited only
Email for the Client, phone for the Customer — and phone for the Client too. Email as the Client credential is right: it is what a document-heavy onboarding needs, it survives a SIM change, and rejection reasons and approval notices are long-form. But every operational step after approval runs on WhatsApp — booking alerts with a 12-hour accept window, check-in coordination, the one-tap availability BLOCK reply, payout notices. A farm owner in Kamrej reads WhatsApp; he does not read email. So phone is collected and OTP-verified during onboarding and is not optional. Email is the credential, phone is the channel.

Dev mode — OTP without an SMS bill

Transactional SMS in India is metered per message and email is effectively free, so paying for a gateway while building the login screen is money spent on nothing. In development, 123456 verifies any email or any phone number.

Real generated codes keep working alongside it, and are printed to the server terminal rather than sent. That matters: it means the actual code path — generate, hash, store, expire, count attempts, consume — is exercised every time you develop, instead of being skipped and discovered broken on the day you switch the gateway on.

OTP behaviour per environment
Environment123456 accepted?Real codeDelivery
development Yes Also works Printed to the terminal. Nothing is sent, nothing is billed.
staging Only for allow-listed test numbers Works Real gateway, real SMS — so you find out delivery is broken before customers do
production Never. The app refuses to boot if enabled. Only path Real gateway
Why an if (NODE_ENV !== 'production') is not enough on its own. A universal OTP is a total authentication bypass — with it enabled, anyone can log in as any email or phone on the platform, including an admin’s. A single misconfigured deploy with NODE_ENV unset would hand over the whole system silently, and nothing would look broken. So the guard is three layers, and the third is the one that actually saves you: the app must refuse to start, not merely decline to use the bypass. A crash on boot is loud, immediate and impossible to ignore; a silently-enabled bypass is none of those things.
// lib/validation/joi/env.js — the existing boot-time env schema.
// Joi already guards server-only config here, so this is where it belongs.

  NODE_ENV: Joi.string()
    .valid('development', 'test', 'staging', 'production')
    .default('development'),

  // Layer 1: opt-in. Absent means off — never default a bypass to on.
  DEV_OTP_BYPASS: Joi.boolean().default(false)
    // Layer 3: in production this value MUST be false. Joi throws on boot
    // otherwise, so a bad deploy crashes loudly instead of silently
    // accepting 123456 for every account on the platform.
    .when('NODE_ENV', {
      is: 'production',
      then: Joi.valid(false).messages({
        'any.only': 'DEV_OTP_BYPASS must be false in production',
      }),
    }),

// ---------------------------------------------------------------------
// lib/auth/otp.js

const DEV_CODE = '123456';

// Layer 2: both conditions, every time. Never cached in a module const,
// so it cannot be captured at import time before env is validated.
function bypassEnabled() {
  const env = getEnv();
  return env.NODE_ENV !== 'production' && env.DEV_OTP_BYPASS === true;
}

export async function verifyOtp({ identifier, purpose, code }) {
  if (bypassEnabled() && code === DEV_CODE) {
    console.warn('[otp] DEV BYPASS used for %s (%s)', identifier, purpose);
    return { ok: true, viaBypass: true };
  }
  return verifyRealCode({ identifier, purpose, code });  // hash, expiry, attempts
}
Two more cheap safeguards. Log a warning on every bypass use, so an accidentally-enabled flag is visible in any log you look at. And render a persistent DEV MODE · OTP 123456 banner on the login screens whenever the bypass is live — it stops someone demoing the app and believing they just saw real authentication, which is a mistake that gets made surprisingly often.
The real reason to sort this out now is schedule, not money. You cannot simply switch on transactional SMS in India when you feel ready. TRAI requires registration on the DLT platform first — register as a Principal Entity, register your sender header, and register each message template — and approvals take days to weeks. WhatsApp Business API templates are approved separately, per template and per language, which the implementation plan already flags. So the dev bypass is not just a cost saving; it is what lets you build the entire login and notification flow while those registrations sit in a queue. Start the DLT and WhatsApp registrations this week, in parallel with development — they are a lead-time dependency, and discovering that the week before launch is the expensive version of this problem.

STAGE 1 · ROLE: CLIENT

Onboarding — from a stranger to a payable, verified person

A person who owns a farmhouse arrives, proves who they are, proves they can be paid, and waits for a human decision. They are logged in from the first minute — what they cannot do yet is publish a property. Nothing here touches a property at all; this gate is about the person.

EXIT CONDITION → account_status = active, set only by a Super Admin decision, never by the system. Email verified, phone verified, KYC verified, payout destination on file, at least one identity document reviewed.

Enter email at /partner/loginCLIENT

One field. We do not ask for a password, ever — there is no password to forget, phish or reset. Submitting creates nothing yet; it only issues an OTP.

Email OTP issued and verifiedSYSTEM

6-digit code, valid 10 minutes, maximum 5 verification attempts, resend allowed after 60 seconds and at most 3 times per hour per email. Only the hash of the code is stored. On success the user row is created with role='client', account_status='pending_application', email_verified_at set.

Logged in straight away, into a dashboardSYSTEM

No waiting room, no “we’ll email you when you’re approved” dead end. A verified email is enough to be inside the product. The row now exists in our database with a reachable identity, which is the difference between a nudgeable lead and an invisible bounce — and the dashboard itself becomes the thing that pulls them through the rest.

The dashboard shows a completion stepper, not an empty shellSYSTEM

Landing on a bare dashboard teaches nothing. Landing on “Farms near Kamrej earn ₹8,000–14,500 a night — 2 of 6 steps done” gives a number to chase and a reason to chase it. See the stepper design below.

Verify phone by SMS OTPCLIENT

A step in the stepper, not a gate before it. Same rules as the email code. This is the channel every booking alert, accept-window reminder and payout notice will use, so an unverified phone blocks submission — it does not block access.

Work through the profile steps, in any orderCLIENT

Saved on every field, resumable from the same email OTP on any device. Order is the Client’s choice — someone who has their PAN to hand but not their bank details should not be blocked by our sequencing. Fields are listed below.

“Add place for rent” is visible the whole time — and gated on clickCLIENT

The primary call to action is never hidden, because hiding it hides the point of the product. It carries a lock, and clicking it opens a sheet naming exactly which steps remain, each deep-linking to that step. See the gated CTA pattern.

Upload identity and payout evidenceCLIENT

PAN or Aadhaar through the KYC provider (never a raw image stored by us — only the vendor’s reference and result), a selfie for face match, and bank account or UPI ID for payouts. See the document vault.

Submit for review → enters the Super Admin queueSYSTEM

application_status moves draft → submitted, and the stepper enters its second phase: “6 of 6 submitted · in review. We reply within 2 working days, by email and WhatsApp.” The Client stays logged in, with full read access to everything they built.

Super Admin reviewsSUPER ADMIN

Against a fixed checklist, with a written reason recorded either way. Three outcomes, never two: approve, reject, or request more information — the third is what stops a fixable typo from becoming a permanent rejection.

Decision deliveredSYSTEM

Approved → account_status='active', email + WhatsApp, and the dashboard now shows Add your first property. Rejected → reason shown verbatim, resubmission allowed. Info requested → back to draft with the specific fields flagged.

Client logs in again — now with full accessCLIENT

Same email-OTP route. The only thing that changed is account_status, which is what the permission matrix reads. There is no second credential and no “approved user” login.

Mixing the two is the most common way this flow goes wrong: it makes Gate 1 impossible to decide cleanly, and it means a Client with three farmhouses has to re-do KYC three times.

The trap this two-phase split exists to avoid. A single bar that fills to 100% and leaves the Add place button still locked is worse than showing no bar at all — the Client has done everything asked and the product still says no, with no explanation. So the review step is rendered as a step, in its own phase, from the very first visit. Derive the progress, never store a step counter. A stored current_step = 4 silently goes wrong the moment reality changes underneath it — a penny-drop that fails on retry, a KYC result that comes back rejected, an admin who requests more information on one field. Compute completion from the data on every render: emailVerifiedAt, phoneVerifiedAt, the required application fields, kycStatus === 'verified', payoutNameMatch, consentAt. Then the bar cannot lie, and a step can legitimately go backwards when something is invalidated.

The gated CTA — visible, locked, and specific

Add place for rent is on the dashboard from the first second. Hiding it hides the entire point of the product; a Client who cannot see what they are working toward has no reason to finish. But the click has a right and a wrong form, and the difference is measurable.

✕ Wrong
Please complete your profile first.

The button looks fully enabled, so the click reads as a failure. The message names nothing, links nowhere, and leaves the Client to hunt for what is missing. This is how a motivated owner becomes a closed tab.

✓ Right
Two things left before you can add a property
  • Add your payout account — 1 min
  • Agree to the terms — 10 sec

Then we review within 2 working days.

The lock sets the expectation before the click. The sheet names the exact remaining steps, deep-links to each, estimates the effort, and states the review wait honestly. Nothing is a surprise.

Same pattern, three other places. Once a Client is approved but has no listing yet, “Add place” becomes the unlocked primary action. Once a listing sits in pending_review, the dashboard shows it with the same honest phase language rather than pretending it is live. And on the Customer side, Book stays visible to a logged-out visitor and opens the phone-OTP sheet on click — never a redirect to a login page that loses the dates they had picked.

STAGE 2 · ROLE: CLIENT, THEN SUPER ADMIN

Adding a place — and proving it is theirs

This is the part you were unsure about, and it splits into two genuinely separate problems: what the Client types in (a long form, best broken into steps), and how we know the property is theirs (a document, name-matched to their KYC). The second one is the whole moat.

EXIT CONDITION → listing_status = live. Requires: complete listing, 6–15 photos, ownership document name-matched, moderation checklist passed, and a completed verification visit (physical or video).

A moderation rule you will need on day one, from real market research. Live listings on competing Surat-belt sites carry house rules such as “Only Hindu can book this property”. Trust fields — the edits that re-open Gate 2

A live listing must stay editable or Clients will not maintain it. But not every field is equally load-bearing. Split them.

Edit classification on a live listing
ClassFieldsEffect of an edit
Free Price, weekday/weekend rates, availability, blocked dates, deposit amount, extra-guest charge, description wording Applies immediately. Stays live. Logged.
Trust RE-REVIEW Photos, hero photo, address or map pin, capacity, bedrooms, category, amenity tags, house rules, title live → pending_review. Existing confirmed bookings are untouched; the listing simply leaves search until re-approved.
Locked Owning Client, ownership document, city/area Not editable. A different owner or a different property is a new listing, not an edit.
Why photos are a trust field and price is not. A Client who swaps in photos of a nicer farm after approval has defeated the entire verification. A Client who raises Saturday pricing by ₹500 has done something completely normal. Treating both the same either blocks routine pricing work behind a review queue, or leaves the biggest fraud vector wide open.

Super Admin listing review — the checklist

Ownership document name-matchADMIN

Does the name on the 7/12 extract, light bill or Index-II match the KYC name? Exact, family-partial, or no match — each has a different path. This is the single check that keeps brokers from posting as owners.

Photo integrityADMIN

Reverse-image search each photo. Catch stock photography and photos lifted from other listing sites. Check for a phone number or Instagram handle on a gate board or watermark in photo #4.

Hidden contact detailsADMIN

Scan title, description and rules for phone numbers, numbers spelled in words, emails and social handles. Automated flag, human decision.

Price sanityADMIN

Compare against the area’s band. A 3BR farm in Kamrej at ₹900 a night is either a typo or bait.

Discriminatory or unlawful termsADMIN

Explicit reject. See the rule above.

Local permissions declaredADMIN

For event-capable properties: has the Client declared they hold the local body permission and meet noise limits? We are not liable for their compliance, but the declaration must be on file and was asked for.

Assign the verification visitADMIN

pending_review → pending_verification. Video walkthrough by default — a scheduled live call, screen-recorded, roughly 70% as convincing as a physical visit and free. Physical visit for high-value listings and once a cluster has volume.

Visit completed and filedVERIFIER

GPS + timestamp so you know the visit happened at the property. Standard photo set, amenities present vs claimed, condition rating, mobile network, approach-road quality, red flags.

PublishADMIN

pending_verification → live, with the Physically Verified or Video Verified badge. The listing enters search, the sitemap, and its area page’s live count.

THE QUESTION YOU ASKED

“What document proves this place belongs to this user?”

You were right to assume something like this exists — it does, and in India it is unusually well defined. For farm land in Gujarat there is a specific record for exactly this purpose. Here is the accepted list, easiest to obtain at the top.

Electricity bill Light bill Possession and a name-to-address link. Easiest to get, and every owner has one. Weak alone — accept for low-value listings, pair with a second doc otherwise

The document vault — one table, strict rules

All uploads, whoever they belong to and whatever they prove, go through one polymorphic store with one review lifecycle. Identity documents are the exception: those never reach us as images.

RuleWhy
Never store a raw Aadhaar or PAN image. Store the KYC vendor’s reference and its verdict.Aadhaar and PAN are sensitive personal data under the DPDP Act. Holding the images makes you a target and a liability for no benefit.
Ownership documents are stored, in a private bucket, server-side encrypted, never public-read.They are the evidence behind a listing badge and may be needed in a dispute.

First required at enquiry or booking, never at browse. Account is active immediately — there is no Gate for Customers. KYC becomes mandatory above a ₹5,000 booking value, which is also what makes a Client comfortable handing over a property.

Ask questions in masked chatCUSTOMER

Contact details hidden on both sides. Phone numbers, numbers spelled in words, emails and social handles filtered, with the sender told why rather than silently stripped.

Pick date + slot, pay the advanceCUSTOMER

Advance is 25% of rent plus the entire platform fee, so revenue is never at risk. Balance either online before check-in or cash on arrival, recorded in-app. Money is held by the platform, not sent to the Client. Booking sits at requested.

Client accepts within 12 hoursCLIENT

Sees the Customer’s badge, past bookings and reviews first. On accept → confirmed, and only now do the exact address, both phone numbers and a check-in code unlock. On decline or expiry → automatic full refund, no questions.

Arrive and check inCUSTOMER

Check-in code verified. The Client or their caretaker captures timestamped condition photos through the in-app camera — gallery blocked — and the Customer co-confirms. A material mismatch reported within 60 minutes is treated as a Client cancellation: full refund, Client penalised.

Check out, inspect, settleCLIENT

Side-by-side comparison against the check-in set. All-OK or a damage claim with evidence inside the inspection window. Deposit auto-refunds when the window closes clean. Payout to the Client on T+1/T+2 with commission, TDS and TCS recorded.

Two-way reviewBOTH

Released only when both sides submit, or after 14 days. Sub-scores for cleanliness, listing accuracy, value and behaviour. This is what feeds the Client’s public signals.

State machine — booking.state

requested →client accepts confirmed →check-in handed_over →check-out returned →window clean completed
requested →decline / 12h expiry cancelled     returned →claim filed disputed →admin decides completed
Note the deliberate asymmetry. requested → cancelled is free and automatic for the Customer — nothing has been promised yet. confirmed → cancelled by the Client is the most damaging event in the whole system: full refund plus a platform credit to the Customer, dates auto-blocked, listing de-ranked, and ops attempts an instant rebook at a comparable property with Rentra paying the difference.
THE ZERO-GAP REGISTER

Thirty things that will happen, and what the system does.

A flow diagram is the happy path. These are the branches that turn into support calls if nobody decided them in advance. Each one has a defined answer. Open any.

Onboarding & identity

01 Client fills half the application and disappears

Saved as a draft, resumable from the same email OTP. WhatsApp nudge at day 2 and day 7. Purged at day 30 with a final notice, because a stale half-application containing a bank account is a liability, not an asset.

02 Email OTP never arrives

Resend after 60 seconds, 3 per hour. After the second failed resend, offer the phone-OTP fallback for login only — the email still has to be verified before the application can be submitted, because that is where rejection reasons go.

03 The same email applies twice

Impossible by constraint — unique on (email, role). The second attempt just logs them into the existing application and shows its status. Never create a duplicate; never show “email already exists” as an error on a login-by-OTP flow.

04 One person wants to be both Client and Customer

Two accounts, one verified human. Uniqueness is on (email, role) and (phone, role), so the same address and number can hold one of each. Both link to a single person row, so KYC is done once — otherwise you pay the vendor twice and ask a verified owner to photograph his PAN again.

05 Penny-drop name does not match the KYC name

Application cannot be approved. Either a payout destination in their own verified name, or a documented explanation reviewed by hand. Paying out to a third-party account is how a marketplace becomes a laundering route.

06 Application rejected — can they try again?

Yes, twice. Reason is shown verbatim so the fix is knowable. Third rejection sets blocked and only a manual appeal reopens it. Rejections must always carry a written reason — a silent no generates a support call and a bad review.

07 Approved Client never lists anything

WhatsApp nudge at day 3, 10 and 30, then an ops call. An approved Client with no listing is a recruitment failure, not a product one — treat it as a founder task, and offer to build the listing for them from photos and a voice note.

08 Super Admin approves by mistake

Every decision is reversible and audited. active → suspended hides all listings while honouring confirmed bookings. The audit row records who, when and why, for both the original decision and the reversal.

The stepper & the gated CTA

09 Client logs in, completes nothing, never returns

This is the case letting them in early exists to catch. The row is in the database with a verified email, and often a verified phone, so it is a lead rather than a bounce. WhatsApp nudge at day 2 and day 7 naming the specific remaining step — “you’re one field from being able to list” converts far better than “complete your profile”. Full purge at day 30, because a dormant half-application holding a bank account is a liability.

10 KYC comes back rejected after that step showed as done

The step goes backwards and the bar shrinks — by design. This is precisely why completion is derived from the data rather than stored as a counter. Explain it in place: “Your PAN check did not pass. Re-check with the name exactly as printed.” A bar that silently stays at 4/6 while the underlying check has failed is the worst outcome, because submission then fails for a reason nothing on screen explained.

11 Client edits their application after submitting it

A submitted application is read-only. Editing requires Withdraw and edit, which moves it back to draft, removes it from the admin queue, and does not count as a strike. Silently allowing edits under a reviewer is how an admin approves a version that no longer exists.

12 Client clicks the locked “Add place” button five times

Log it — it is the strongest intent signal you will get. Someone hammering a locked CTA is telling you they have a property ready and are stuck on paperwork. Surface it in the admin queue as a priority sort, and treat repeated clicks as a trigger for an ops call rather than another automated nudge. At MVP scale that call is the highest-value use of your time.

Listings & ownership

13 Ownership document is in a father’s or HUF name

The most common real case, and it is not a rejection. Request relationship proof plus a signed no-objection from the recorded holder. If unavailable, the Client proceeds as authorised_agent and the listing says Authorised manager publicly. Never approve as owner on a mismatched name.

14 Client uploads someone else’s photos

Reverse-image search on upload, before review. A hit blocks submission with the reason. Confirmed intentional theft suspends the account on the first offence. Prefer verifier-shot photos as the primary gallery precisely because it removes this vector.

15 Phone number hidden in a photo, on a gate board

Part of the moderation checklist, not an afterthought. Also OCR the images. This is the most common bypass attempt and it is invisible to text filters.

16 Client edits photos on a live listing

live → pending_review. Photos are a trust field. The listing leaves search; confirmed bookings are untouched. The previously approved version is retained so the admin can compare, which is how you catch a swap rather than a genuine reshoot.

17 Client changes only the Saturday price

Applies immediately, stays live. Price is a free field. Putting routine pricing work behind a review queue guarantees stale prices, which is worse for everyone than the risk it avoids.

18 Verification visit finds the property does not match

Listing rejected with the report attached, and every other listing by that Client is flagged for re-check. One fabricated listing is strong evidence about the rest — this is the check most systems miss.

19 Two Clients list the same property

Detected on map pin proximity plus address similarity at submission. Both go to manual review; the one with the stronger ownership document wins, the other is rejected. Without this check a broker and an owner can both list one farm and double-book it.

20 House rules contain a discriminatory restriction

Explicit reject, with the rule quoted back. Religion, caste, marital status, region, single-women restrictions. Offer the legitimate structured alternatives instead. This is live on competitor sites today — do not inherit it.

Bookings, money & suspension

21 Two Customers book the same slot at the same instant

Postgres decides, not the UI. The composite primary key on availability(rentable_id, day, slot) means the second write fails inside the transaction. The loser sees “just taken — here are 3 similar farms on that date”, and is never charged.

22 Client never responds to a booking request

12-hour timer in the worker. On expiry: full automatic refund, slot reopened, response rate reduced, listing de-ranked. Repeated non-response is a suspension trigger. Slow response is the number one cause of lost bookings on Indian rental platforms.

23 Client is suspended while bookings are confirmed

Listings hide; confirmed bookings are honoured. Punishing a Customer for their Client’s misconduct is the worst possible trade. Payouts freeze until the case closes; ops contacts each affected Customer personally.

24 Client asks to delete their account with future bookings

Blocked, with the reason and the date shown. Listings can be paused immediately so nothing new arrives; deletion completes once the last booking reaches completed and the retention period for its financial records has run.

25 Customer pays but the Client’s listing was hidden meanwhile

Cannot happen — availability is locked at payment, not at accept. If the listing is hidden between request and accept, the request is auto-cancelled with a full refund and an apology credit, and ops attempts a rebook.

26 Caretaker, not the Client, is at the property for check-in

This is the normal case, not the exception. The Client adds a staff sub-account with scoped permissions: can check in, can capture condition photos, cannot see earnings, cannot change price. Without it, the condition-photo requirement — which the entire dispute process rests on — simply will not be complied with.

27 Customer balance was paid in cash and nobody recorded it

Both sides confirm the cash handover in-app at check-in. Commission was already taken with the advance, so revenue is safe either way. A Client who takes cash and does not confirm gets a nudge, then a ranking penalty. Fighting cash loses; instrumenting it wins.

28 Super Admin is unavailable and the queue backs up

Publish the SLA and measure it: 2 working days for applications, 2 for listings. Show queue age on the admin dashboard, and alert past SLA. At MVP scale you are the only reviewer — so the honest mitigation is that verification throughput caps your growth rate, and you plan recruitment around it rather than pretending otherwise.

Auth & delivery

29 The dev OTP bypass reaches production

The app refuses to boot. Joi validates DEV_OTP_BYPASS against NODE_ENV at startup and throws in production, so a bad deploy crashes loudly rather than silently accepting 123456 for every account — including an admin’s. Declining to use the bypass is not enough; the process must not start. See dev mode.

30 SMS silently stops delivering in production

Assume it will, and instrument it. Indian transactional SMS depends on TRAI DLT registration and per-template approval, and a template edit or an expired header kills delivery without any error your code can see. So: log every send with the gateway’s response id, alert on delivery rate falling below a threshold, and keep email OTP as a working fallback for Clients — which they already have, because email is their credential. A Customer who cannot receive an SMS should be offered a WhatsApp OTP before being offered nothing.

WHAT THIS NEEDS FROM THE DATABASE

Seven new tables, three enum changes.

The current schema already carries user, rentable, availability, booking, payout, review, client_staff and person. What the flow above adds is the machinery for credentials, applications, documents, review decisions and audit — none of which exists yet.

-- ============ CHANGES TO EXISTING TABLES ============

user  -- add:
  email              varchar(254)   -- Client credential
  email_verified_at  timestamptz
  phone_verified_at  timestamptz
  account_status     enum('pending_application','active',

listing_status  += 'rejected'

-- ============ NEW TABLES ============

-- One-time codes. Only the HASH is stored, never the code.
otp_token (
  id, identifier,           -- the email or phone
  channel enum('email','sms'),
  purpose enum('login','verify_phone','verify_email'),
  code_hash, expires_at, attempts int, consumed_at, created_at
)
  INDEX (identifier, purpose, expires_at)

-- Gate 1. One per Client, with its own review lifecycle.
client_application (
  id, user_id UNIQUE,
  status enum('draft','submitted','more_info_needed',
              'approved','rejected'),
  legal_name, residential_address, pincode,
  client_type, owner_name, owner_relationship,   -- agent path
  payout_upi_id, payout_account_ref, payout_name_match bool,
  intended_listing_count int,
  consent_at, consent_ip,
  submitted_at, reviewed_at, reviewed_by → admin_user,
  decision_reason text, flagged_fields jsonb,
  strike_count int DEFAULT 0
)

-- Polymorphic vault. Ownership docs live here; ID images NEVER do.
document (
  id, owner_type enum('client_application','rentable','booking'),
  owner_id,
  doc_type enum('electricity_bill','property_tax','extract_7_12',
                'extract_8a','index_ii','sale_deed','na_order',
                'authorisation_letter','owner_id','noc'),
  storage_key,                -- private bucket; signed URLs only
  name_on_document, name_match enum('exact','partial','none'),
  issued_at,                  -- freshness rule: bills < 3 months
  status enum('uploaded','accepted','rejected','superseded'),
  reviewed_by → admin_user, review_note, uploaded_at
)
  INDEX (owner_type, owner_id, status)

-- Gate 2. One row per review pass, so history is preserved.
listing_review (
  id, rentable_id, pass_number int,
  checklist jsonb,        -- {ownership, photos, contacts, price, rules, permits}
  outcome enum('changes_requested','approved_for_visit',
               'published','rejected'),
  reason text, reviewed_by → admin_user, reviewed_at
)

-- The verification visit. GPS proves it happened AT the property.
verification_visit (
  id, rentable_id,
  mode enum('video_call','physical'),
  assigned_to, scheduled_at, started_at,
  geo_lat, geo_lng,          -- captured on site, compared to the pin
  report jsonb,             -- amenities claimed vs present, condition,
                            -- network, approach road, red flags
  outcome enum('passed','failed','no_show'),
  recording_key, completed_at
)

-- Every consequential action, by anyone. Non-negotiable.
audit_log (
  id, actor_type enum('client','customer','admin','system'),
  actor_id, entity, entity_id, action,
  before jsonb, after jsonb, reason, ip, at
)
  INDEX (entity, entity_id, at)

-- Fixed amenity taxonomy. Tags are PICKED, never typed.
amenity (
  id, slug UNIQUE, group_slug,
  label_en, label_hi, label_gu,
  value_type enum('none','count','dimensions','area','charge'),
  is_filterable bool, sort_order int
)
rentable_amenity (rentable_id, amenity_id, value, PRIMARY KEY(both))
Two of these are worth building even though nothing reads them yet. audit_log, because the first time a Client disputes a suspension you will need to show what happened and when, and you cannot reconstruct it later. And approved_snapshot on rentable, because diffing an edit against the last approved version is the only way to tell a genuine reshoot from a photo swap.
One migration hazard, already hit once on this project. Adding a NOT NULL column with no default to a table that has rows fails. Every one of these additions to user and rentable must go in as nullable → backfill → constrain, in three statements. Drizzle will not generate that for you.
BUILD ORDER

The order that keeps the app runnable at every step.

Each step leaves the system in a working state and is independently demoable. Nothing here needs a Customer to exist until step 8, which is the point — supply first.

What already exists and does not need rebuilding: the rentable / availability / booking / payout schema with the double-booking lock, the (phone, role) uniqueness rule, the pricing and refund domain functions, the listing card and slot selector, the design tokens, and 12 seeded listings with 90 days of availability. Steps 1–7 are additive; nothing above throws any of that away.

The flow in one line: Super Admin exists first, the Client proves who they are, then proves each property is theirs, and only then does a Customer ever see it — with a written, audited human decision at both gates and a defined answer at every branch.

The two things most likely to be got wrong: collapsing the two gates into one, which either leaves you paying unverified strangers or lets an approved Client publish a farm they have never seen; and treating a photo edit like a price edit, which is the widest fraud vector in the whole system.
