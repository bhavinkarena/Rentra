01 / Product decisions

Build the whole guest journey around one clear promise.

“Find a space you understand, choose the dates you need, and always know where your booking stands.” This is a customer requirements and implementation plan. It complements the existing owner plan; the application and database are not changed by this document.

D01 · Product scope

Farmhouse and space bookings first

One listing, one customer, INR and a property timezone per order. Support day picnic, overnight and the existing full-day product only where the owner has defined precise start/end times. Keep goods, multi-property carts and recurring subscriptions outside this release.

D02 · Multiple dates

Both consecutive and separate dates

Single date, consecutive start/end dates, or a set such as 3, 10 and 17 October. Each becomes an individual visit within one order. Initial checkout uses the same slot and guest count across visits; later changes must never silently alter other dates.

D03 · Booking confirmation

Confirm immediately in the current flow

After customer login, a valid quote and atomic inventory allocation, confirm the booking and create a simulated transaction. Do not send it into an unbuilt owner acceptance inbox. This intentionally replaces the old “request booking / wait 12 hours” concept for this customer release.

D04 · Payment integration

Prepare the data now

Create order, attempt, transaction, refund, allocation and payment-method structures before integrating a gateway. The server creates a DUMMY_… transaction ID, records zero actual collection, and excludes these transactions from payout and revenue totals.

Working defaults for implementation: maximum 10 visits per order; property timezone Asia/Kolkata for current listings; an order holds one listing and one currency; 10-minute checkout holds; no inventory hold while logging in. These are proposed product limits, not observations about competitors. Centralise them as configuration.

Existing public pricing rules remain the starting point: 8% platform fee; an illustrative future advance of 25% of rent plus the fee; security deposit shown separately. This plan changes how safely these values are represented, not the commercial rates. Tax treatment and future collection schedules require an explicit policy before real payment launch; no tax rate is assumed here.

Authentication and account behaviour

Continue where you left off

Store a validated, short-lived booking selection containing listing ID, local dates, slot and guest count. Requote after login; store no trusted totals in browser state. Favourites merge once and idempotently.

Reuse the role model safely

The repository treats each account as one role and permits separate customer/partner accounts sharing a phone through role-scoped uniqueness. Add customer login actions and reuse requireCustomer(); an active wrong-role session needs an explicit switch/re-login. Do not block customer signup merely because a partner account uses the same phone. Verify roles and ownership within queries and actions, not just in layouts or navigation.

OTP requirements: short expiry, one-time use, hashed challenges, attempt caps, phone/IP rate limits and a real configured delivery adapter. Developer OTP shortcuts must be disabled in public production. Session cookies should be secure, HttpOnly and explicitly scoped; sensitive actions re-check the database session/user state.

Calendar and quote rules

Selection validity

  • 1–10 unique visits; same listing, currency, slot and guest count in v1.
  • Disable past start times, owner-blocked dates, capacity conflicts and missing inventory. Respect listing lead time, published booking horizon and slot-specific guest limits.
  • Show each date’s actual price including an override. Changing guests or slot revalidates every selected date.
  • Do not clear valid choices when one date fails; explain exactly which dates need attention.

Price and policy validity

  • Server quote includes quote ID, version, expiry, exact visit intervals, per-visit charges and policy/deposit snapshots.
  • Changing prices or terms requires a new accepted quote before confirmation.
  • Amount arithmetic uses integer minor units. Display INR clearly, with paise if needed; never use floating-point totals as stored money.
  • Do not calculate a weekend by the browser timezone. Use each visit’s local start date.

Inventory protection: a real interval, not just a coloured square

Retain existing availability rows for owner blocks, rates and calendar inputs, but make a new inventory_reservation ledger authoritative for held/booked usage. Store both visit times and buffer-inclusive blocked times. Public availability is derived from this ledger plus owner inputs; it is advisory until revalidated in the booking transaction.

  1. Validate the active customer and normalise/sort all dates. Resolve owner-defined start/end times and turnover buffers into UTC timestamps, preserving Asia/Kolkata and local visit dates.
  2. Start a database transaction. Lock the listing inventory mutex first, then any affected order rows in stable ID order, then reservation/payment rows. Every booking, cancellation, expiry and owner-block writer follows that order, including operations that expire other orders’ stale holds. Discover IDs without locking, then revalidate after acquiring locks. For a future multi-listing operation, sort listing IDs first.
  3. Under the listing lock, expire stale holds conditionally and check all active reservations plus owner blocks for actual interval overlap. For the initial exclusive farmhouse inventory, prevent overlapping blocked ranges using a database exclusion constraint as defence in depth. Future multi-unit inventory requires a unit allocator/capacity check.
  4. Recompute the quote from current rates and verify its accepted version and policy. If any date, interval or capacity fails, roll back the entire new order/hold and return the exact conflicts. The guest explicitly chooses whether to remove them.
  5. Insert the complete group and its reservations atomically. Commit before calling any external provider. During dummy confirmation, commit every visit plus the simulated payment records together.
  6. Cancellation and expiry move each reservation from active to released exactly once. Derive remaining inventory from active allocations; if the old unitsAvailable count remains as a cache, update/rebuild it through this same service and never treat it as a second authority.
Release blocker: the current overnight/day overlap and ambiguous full-day window must be resolved with explicit listing hours. Until hours and buffers are migrated, disable incompatible adjacent combinations. A date/slot primary key or an availability fetch before an INSERT cannot prevent two customers taking the same physical space.

For a single-unit listing, the proposed exclusion key is the listing ID plus a half-open [blocked_start_at, blocked_end_at) range for held/committed reservations. A required GiST equality extension must be verified in the target database during migration. Expired holds leave the active state before new allocation; do not put time-dependent “now” expressions in the constraint predicate. A cleaning buffer extends blocked time, not the guest’s paid access time.

Order: draft → held → confirmed → completed, with expired, cancelled and mixed-child display states. Existing visits retain confirmed → handed_over → returned → completed, plus cancellation/dispute handling. Use requested only if a real host acceptance feature is built later.

Money lifecycle

Payment attempt: created → processing → authorised → captured or failed / cancelled. simulated is its own terminal result. Refund: requested → processing → succeeded / failed, with a separate simulated outcome. A transient timeout is “unknown/processing,” never automatic failure.

Future payment correctness: verify checkout signatures against the server’s stored order, verify webhook authenticity, deduplicate provider events, and tolerate repeated/out-of-order deliveries. The browser’s success screen cannot mark an order paid. Razorpay’s documentation describes signature verification and duplicate event identification; these are prerequisites for the future adapter. [7] [8]

A late capture after a hold expires must not force an overbooking: under the same inventory lock, reacquire all visits only if policy and availability permit; otherwise mark the capture for refund and show a pending-resolution message. A webhook processor stores verified events durably before acknowledging, retries processing, checks expected amount/currency/order linkage and prevents captured state from being downgraded by an older failure event. No external network calls inside database transactions.

Payment-method handling: store provider customer/token references, type, brand and last four only where returned and permitted by the chosen provider. Never store PAN, CVV, UPI PIN or bank-login credentials. The account’s default preference is not a payment authorisation. The existing balance-payment mode describes collection timing and must remain separate from method type.

Migration sequence that respects the existing schema

  1. Expand: add tables, nullable parent linkage, explicit currency/provenance/minor-unit/timestamp fields and supporting indexes. Review the generated Drizzle SQL before running it.
  2. Audit and backfill: one parent order per legacy booking, retain all IDs, identify seed/demo records and unknown historical settlements. Convert existing whole-rupee amounts ×100 exactly once with a migration marker. Do not infer a captured payment from a completed booking or seed payout.
  3. Reconcile: compare row counts and rupee/minor-unit totals, references, price snapshots and interval definitions. Rebuild active inventory only from verified current holds/bookings; historical completed/cancelled visits must not block dates.
  4. Constrain: enforce valid amounts, required FKs, unique keys and interval protections after backfill validation. Existing bookings with unknown hours need explicit remediation before their dates can be sold.
  5. Switch reads and writes: deploy one group-aware booking/quote/payment service, customer DTOs and derived availability. Update owner calendar/inbox readers for the child bookings and grouped reference. Remove old pricing/count logic only after parity checks.
  6. Release safely: activate dummy flow after gates pass; monitor conflicts, duplicate writes and zero real-money totals. A rollback disables new checkout while preserving committed booking records and their inventory; never drop data to roll back a UI deployment.
Money-unit trap in this codebase: lib/domain/pricing.js documents whole rupees and its helper named paise only rounds. Add explicit _minor naming, currency and one conversion boundary. Keep legacy rupee fields read-only during migration; do not mix the two units in refund or payment calculations.

13 / Phased implementation

Deliver in dependency order, with a working result at every gate.

All checklist items start as planned work. Phases U0–U5 deliver the complete customer experience with simulated transactions. U6 enables real payments. These are dependency-based phases, not unsupported delivery-date estimates.

U0

Make availability and money definitions trustworthy

Foundation · blocks checkout and definitive pricing claims

Exit gate: a blocked date cannot be quoted; day/night/full-day overlaps are rejected; calendar and quote agree on overrides; legacy conversion reconciles; no private coordinates are serialized publicly.
U1

Customer identity and the shared visual system

Depends on U0 definitions · design work can start alongside U0

Exit gate: a new guest can log in, return to their selection, save across devices and access only their own account data; an OTP cannot be replayed concurrently.
U2

Discovery and a detail page people understand

Depends on quote foundation · uses shared components from U1

Exit gate: a guest can discover an available listing, understand its rules and select up to 10 valid visits; every displayed final price matches the accepted server quote.
U3

End-to-end booking with a persisted dummy transaction

Depends on U0–U2 · first complete reservation milestone

Exit gate: one- and multiple-date bookings survive refresh/retry; a last-slot race has one winner; conflicting dates produce no partial order; dummy transactions always show ₹0 collected.
U4

After booking: cancellation, support and reviews

Depends on persisted bookings and per-visit allocations

Exit gate: cancelling one of three visits leaves two intact, duplicate cancellation does not release twice, no simulated refund is presented as real, and only genuine eligible visits can produce published reviews.
U5

Customer release quality

Full dummy-payment customer release gate

Exit gate: the whole public customer journey works without dead-end buttons; staff can see and support the resulting bookings; operational failures have visible recovery paths.
U6

Real payment provider integration

Later phase · complete structures already introduced in U0/U3

Exit gate: verified captures, partial refunds, expiry races and retries reconcile without double charges, double refunds or overbooking; account methods can be removed and actual money copy is accurate.
Owner-side dependency: confirmed child visits must appear in an operational owner/admin view, and owner blocks must use the same inventory service. Reuse the companion owner plan’s calendar/inbox work where possible. The customer release cannot depend on staff noticing bookings only in database rows.

Later enhancements after evidence of use: comparison of two or three saved places, named/shared wishlists and notes, saved searches, live messaging with staff coverage, configurable per-visit guests/slots, continuous overnight stays, coupons, add-ons, multi-property carts and international currencies. These are not substitutes for finishing the launch flow above.

15 / Measure the experience

Measure whether people can finish what they came to do.

Customer funnel

search_submitted → listing_viewed → dates_selected → quote_ready → login_completed → checkout_started → booking_confirmed. Measure conversion separately for single versus multiple dates, mobile versus desktop and new versus returning customers.

Return and trust

Save-to-detail and save-to-booking rates; share attempts/completions where observable; history return visits; completed-visit review rate; cancellation and support reasons. Do not assume invoking a share sheet means someone shared.

Operational reliability

OTP delivery failure, quote changes, inventory conflicts, hold expiry, duplicate-submit recovery, outbox delay and unresolved support requests. Alert on negative inventory, active interval overlap or unreconciled actual funds.

Keep simulation separate

Record payment_mode=simulated on relevant events. Report booking-value intent separately from actual collected revenue. Do not count demo document interactions or seed rows as real conversion.

Use pseudonymous internal identifiers and bounded event properties. No raw phone, OTP, access code, payment token or exact address in analytics. Establish baseline rates after release, then set improvement goals; no fabricated conversion targets.
