Part 1

Brand mark

Two SVGs were delivered — a mark and a horizontal lockup. Both needed correcting before they could be used, and neither correction touched the artwork itself.

What was wrong with the delivered files

The ink bounds were measured analytically (parsing the path data and resolving curve extrema) rather than eyeballed, because the visible problem and the actual problem were different sizes.

ProblemMeasuredConsequence if shipped as-isFix
Dead canvas in the lockup 17% of width empty on the right, 20 units below the baseline height:28px would render ~18% smaller than asked, and the artwork hangs high-and-left whenever it is vertically centred in a flex row viewBox cropped to the measured ink box
Wordmark undersized cap height was 40% of the mark's height “Rentra” reads as a caption sitting next to the mark rather than as part of one lockup scaled to 52%, the usual proportion for a horizontal lockup
Colours were left exactly as delivered. The greens (#1F5C41 / #5C9A72) already sit within a few RGB points of brand-700 and brand-400, so nothing clashes with the palette. Snapping them to tokens would have been a brand decision dressed up as a technical one.

The vendored fonts

assets/fonts/PlusJakartaSans-500.ttf and -700.ttf are committed on purpose. Satori (which renders every OG image) has no filesystem and no system fonts, and next/font self-hosts Plus Jakarta Sans as .woff2, which satori cannot parse. Fetching from Google at build time would make the build need the network.

These must stay the latin-ext subset. The latin subset is 229 codepoints and does not include U+20B9 ₹ — every price on every share card renders as a wrong glyph. latin-ext is 523 codepoints and a strict superset. Both facts were verified by reading the fonts' cmap tables, not assumed.

Part 2

Listing detail page

/listing/[slug]-[code] — the page a WhatsApp forward lands on. Built to the section order in the design system, because that order is learned behaviour and deviating from it costs conversion without buying distinctiveness.

Four client islands, and everything else is a Server Component. Every word a crawler reads is in the HTML. The amenities “show all” is a <details> rather than a toggle component, so the hidden amenities stay in the markup, the control needs no JavaScript, and it is keyboard-accessible for free.

How the three booking surfaces stay in agreement

The picker, the sticky price box and the mobile bar are three separate islands, so the selected date and slot cannot live in one component's state. They share the Redux search slice through components/rentra/listing/booking-state.js.

  1. The server picks a sensible default The cheapest slot this farm sells (cheapestSlot()), and the first date that slot is actually free. The panel therefore opens on a real price instead of an empty state.
  2. A date the guest already chose wins Arriving from the header search bar with “Sat 14 Feb / Day picnic” and landing on a listing that has forgotten both is a small betrayal that loses bookings, so the store's value takes precedence over the default.
  3. One function decides what a date costs rentFor() — a per-date owner override beats the weekend rate, which beats the weekday rate. The picker, the price box and the bar all call it, so they can never disagree about whether a Saturday is peak.
The booking bar always wins the bottom of the screen. The bar sets data-booking-bar only while it is actually visible, and globals.css uses that to lift the WhatsApp float via an inherited --float-bottom custom property. No measuring, no resize listener, and no coordination between the layout and the page through JavaScript.

Part 3

Data layer

All in lib/db/queries.js, which already served the public, indexable pages. Nothing here goes through RTK Query.

QueryStateWhat it does
getListingByCode extended Added farmSize, farmSizeUnit, poolSize, checkInFrom, checkOutBy, areaId, cityId, categoryName, verifiedAt, review sub-score averages, and client.firstName
getNextAvailableDates new Next N bookable dates per slot. full_day is derived by intersecting day and night, since it consumes both halves
getSimilarListings new Same area first, then same city, then verified, then best rated. Deliberately not a PostGIS radius — a guest comparing farmhouses thinks in areas, not kilometres
getListingIdByCode new Code → id only, so the availability endpoint does not pay for a full listing join on every calendar paint
cheapestSlot (pricing.js) new Shared by the page, its metadata and its OG card so all three quote the same figure
Correctness fix, found while extending the review query. It did not filter publishedAt. Reviews are two-way and are released only once both sides submit or 14 days pass, so an unpublished review was publicly renderable — a guest's words shown before the owner has had their say. Now filtered, and the sub-score averages are computed in SQL over every published review rather than over the ten loaded for display.

Part 4

The availability endpoint

GET /api/listings/[code]/availability — the one piece of this page that is fetched in the browser.

Why this exists when /api/* is otherwise reserved for external callers. The implementation plan is explicit: “the static shell carries price and the next three available dates. Live availability for the date picker is fetched client-side, so the cached page never shows a stale calendar.” The page is ISR-cached for an hour, and a calendar rendered from an hour-old cache invites a guest to pick a Saturday that sold twenty minutes ago. It is a plain fetch, not RTK Query — that store is scoped to authenticated, noindex surfaces, and this data is public. 
// Request
GET /api/listings/wdlcj85b/availability?days=90

// Response — one entry per date, so the picker does no grouping
// and a 90-day payload stays a few KB on a mid-range Android
{
  "from": "2026-09-07",
  "days": {
    "2026-09-07": { "day": true, "night": true, "full": true },
    "2026-09-08": { "day": true, "night": false, "full": false }
  }
}

// Cache-Control: public, max-age=0, s-maxage=60, stale-while-revalidate=120
  • full is derived server-side, never trusted from the client — a full day consumes both halves, so both must be free.
  • A past from is clamped to today, however the caller asks for it.
  • days is bounded to 1–120; anything else is a 400.
  • An unknown or unpublished listing both return 404 — an unpublished listing should not be discoverable by probing this endpoint.
  • The picker degrades rather than dying: if this fetch fails, the section falls back to the server-rendered next dates instead of showing a dead calendar.

Part 5

SEO, metadata and caching

Real data in the title and description

A templated title with no numbers in it ranks like a template, so generateMetadata builds from the row: 

<title>Green Valley Farm, Kadodara — from ₹6,500 · Rentra</title>
<meta name="description">Green Valley Farm in Kadodara, Surat. Up to 30 guests,
2 bedrooms, a private 15x25 pool, from ₹6,500 per slot. Day picnic or overnight,
money held until check-in, zero brokerage.</meta>

Structured data

LodgingBusiness + AggregateOffer + BreadcrumbList, as the plan specifies. Two deliberate omissions:

  • No geo and no street address. Publishing the exact coordinates in JSON-LD would hand out the address the page itself withholds until a booking is confirmed.
  • No aggregateRating until real reviews exist. Marking up a rating nobody left is what gets a site's rich results pulled.

The listing share card

A per-listing opengraph-image.js, because a forwarded WhatsApp card is seen by more people than the homepage. It carries the price and the next open date — “₹6,500 · Mon, 7 Sept available” converts; “Rentra — book verified farmhouses” does not. A listing that has gone away still renders a valid card rather than a 500, because old forwards keep resolving the URL for months.

Freshness

ConcernMechanismStatus

308 vs the plan's 301. The code resolves the page, never the slug, so a retitle can never 404. permanentRedirect is the App Router's permanent redirect and 308 is its status. Both are permanent and search engines consolidate them identically; 308 additionally forbids the method rewrite that 301 permits, which is irrelevant for a GET page. A literal 301 would have to come from middleware.

Part 6

Information release ladder, as enforced

A browsing visitor with no login sees photos, amenities, price, the area circle and reviews. Everything else is held back — and held back in the query, not just in the markup.

WithheldHowWhy that way
Owner's phone number The column is never selected for a public page. The card renders a masked row with an unlock note There is nothing here to leak even if the markup is wrong
Exact address Not selected; not in the JSON-LD either Same reason. The map is a drawn area circle, so there is no coordinate on the page to reverse
Owner's full name First name only, split server-side The ladder grants the first name at the enquiry stage; nothing needs the surname
The area circle is drawn, not fetched. A real tile provider here would need a key and a third-party request on every listing view — and would tempt someone into dropping the true coordinates into it. The panel is an inline SVG: concentric circles, a dashed area boundary, and the area name. It encodes the rule instead of relying on someone remembering it.

Part 8

Bugs found and fixed

Four of these were pre-existing or environmental. One was introduced during this build and caught in review.

1 · ISR was not caching the listing page at all

Symptom
Response came back Cache-Control: private, no-store with no x-nextjs-cache header on repeated requests.
Cause
export const revalidate alone does not cache a dynamic segment. Without generateStaticParams, every request rendered the page from scratch.
Fix
Added generateStaticParams. All live listings now prerender with a 1h revalidate and serve x-nextjs-cache: HIT.
Note
At a few thousand listings, return only the ones worth prerendering and let the long tail fall through to on-demand ISR.

2 · The WhatsApp float sat behind the mobile booking bar

Symptom
The float overlapped the price in the sticky bar, breaking the design system's “the booking bar always wins the bottom of the screen”.
Cause
The first fix was a plain rule on .whatsapp-float, which silently lost to Tailwind's own bottom-5 utility — utilities are a later cascade layer, so no amount of selector specificity wins.
Fix
The float positions itself with bottom-(--float-bottom), and the variable is redefined under body:has([data-booking-bar]). Inherited custom properties are not subject to layer ordering.

3 · ₹ rendered as a wrong glyph on every share card

Symptom
₹7,500 appeared as ≡7,500 in the generated OG PNG.
Cause
The vendored font was Google's latin subset, which excludes U+20B9. Confirmed by parsing the font's cmap table rather than guessing.
Fix
Swapped to latin-ext — 523 codepoints, includes ₹, and verified to be a strict superset of latin.
Note
The website has the same gap and only survives it because browsers fall back per-glyph. Satori has no system fallback, which is why it surfaced here first.

4 · Unpublished reviews were publicly renderable

Symptom
The listing review query did not filter publishedAt.
Cause
Reviews are two-way and release only when both sides submit or 14 days pass; the gate existed in the schema but not in the query.
Fix
Filtered to published only, for both the displayed list and the sub-score averages.

5 · The primary CTA had near-black text on brand green introduced here

Symptom
“Request booking” rendered dark-on-dark — barely legible, and the most important control on the page.
Cause
<Button> runs its classes through tailwind-merge, which cannot know that meta is a font-size in our @theme. It read text-meta as a text colour and dropped the variant's text-primary-foreground, leaving the label to inherit --foreground.
Fix
Used text-base, which tailwind-merge recognises as a font size. Same 16px, and the colour class survives.
Standing rule: never put a custom @theme font-size token on <Button>. text-meta, text-body, text-tiny, text-h4 and friends will all strip the button's text colour. Use text-sm / text-base. Re-asserting the colour afterwards does not help — tailwind-merge then drops the font size instead. Plain <button> elements are unaffected, since nothing merges their classes.

Part 11

Open gaps

Known and deliberate. None of these are hidden behind a “TODO” in the code without also being here.

“Request booking” does not submit anything yet. The button is styled, sized and positioned, and the price it quotes is correct — but there is no checkout route and no Server Action behind it. The validation schema (bookingRequestSchema) already exists; the flow itself (advance payment → 12-hour acceptance timer → confirmation) is the next piece of work.
  • revalidatePath() on owner edit is not wired. Until it is, an edited listing takes up to an hour to appear. The call belongs in the partner-side Server Action that saves a listing.
  • components/rentra/PriceBox.jsx is now unreferenced. BookingPriceBox supersedes it. Left in place in case it is intended for the checkout screen — delete it if not.
  • The listing OG card is typographic, not photographic. Using the hero photo would mean either reading from public/ at runtime (which breaks on serverless, where public/ is not in the bundle) or a network fetch per card. Worth revisiting once listing photos live on a CDN.
  • The area map is drawn, not a real map. Intentional — see the release ladder. If a tile provider is ever added, it must render the area circle, never a pin.
  • Reviews show three sub-scores. cleanliness, accuracy and valueForMoney. behaviour is an owner-side score about the guest and is not shown publicly.
  • Amenities are free-text strings. The fixed amenity taxonomy exists in the schema, but rentable.amenities currently holds labels, so icons are matched on keywords. Moving the page onto rentable_amenity would make them filterable and translatable.
  • The mobile lightbox has no swipe. Keyboard and buttons work; touch gestures are not implemented.
